## 0.1.0-alpha.1 (2026-10-20)

The first release, and an alpha: until 0.1.0, an alpha may change the API, and what two builds share.

- **API.** `Builder::new(app, state)` takes the app id and the folder the app keeps its state in (`State::dir`, or `State::none` for an app that keeps no files). It is configured with `scope`, `dir`, `guard`, `elevated_owner`, `hand_down`, `timeout` and `payload_version`, and ends in `start`, `hand_off`, `probe` or `exclusive`. `start` returns `Started::{Owner(Claim), HandedOff(OwnerInfo), Alone(Reason)}`, and a `Claim` is served with a handler (`claim.serve(|r| tx.send(r).is_ok())`) once the app has somewhere to send requests. `AppId::windowed` and `AppId::headless` give an app id its kind. `exclusive` holds the state for batch work and serves nothing. The public API has no `futures` or `serde` types.
- **Payloads.** The `Payload` trait, implemented for `Args` (argv, lossless), `Vec<u8>`, `String`, `()`, and `Json<T>` with the `serde` feature. The launch's working directory and activation tokens travel beside every payload.
- **One owner per state.** Launches of one app id by one user that name one state folder and one scope meet one owner, whatever their Windows integrity level, session or display. The state folder's links are resolved first. The owner also holds a guard, a lock on `.instance-handoff.lock` in the state folder, so a launch that took its lock in another runtime folder (another container, or another `Builder::dir`) runs alone with `StateInUse`. Owners with a scope share the guard. None is taken under `Guard::Off`, for `State::none`, on a network file system, or where the file system can't lock files. `start` and `exclusive` make a missing state folder, private, and refuse one that belongs to another user with `ForeignState`. An owner that holds the guard ends with `End::LostState` if the state folder is removed or replaced under it.
- **Kinds.** Only a launch that can show windows owns a windowed app: one from `ssh`, cron or a service hands off, or runs alone with `MayNotOwn { why: NoWindows }`. A headless app's launches need no display to own. Both kinds of an id meet at one lock, and a launch of the other kind than the owner's gets `OtherApp`.
- **No duplicate delivery.** A launch commits its request only inside its timeout, and the owner calls the handler only after the commit. So a launch that ran alone is never also delivered, even when the owner was suspended, slow or killed.
- **Concurrent serving.** One thread serves every connection at once, so a silent or slow client delays nobody.
- **Lifecycle.** Dropping an `Owner` or a `Claim` keeps the lock and the guard until the process exits; `release()` frees them. Dropping an `Exclusive` releases the state at once. `stop()` wakes the thread at once and drops the handler. `on_end` and `Owner::ended` report `Stopped`, `Panicked`, `LostLock` or `LostState`.
- **Reasons.** `Reason` is an error enum with a variant for every outcome, and every variant can gain fields later. An owner that refuses a launch sends the cause at once and never just closes, so a refusal never waits out the timeout. A launch reads a cause it doesn't know as `Declined`.
- **Folders.** One right folder per launch, never a fallback. The app's folder is `/run/user/<uid>/<id>` on Linux with systemd, `/tmp/<id>-<uid>` on Linux without systemd and on the BSDs and illumos, and `<id>` in the sandbox's runtime folder in Flatpak and snap, in the per-user temporary folder on macOS, in `$TMPDIR` on Android, and in Local AppData on Windows, which is refused when it resolves into another user's profile. Root's is fixed, whether or not root is logged in: `/run/instance-handoff/<id>` on Linux outside Flatpak and snap, and `/var/run/instance-handoff/<id>` on the BSDs and illumos. The lock is in the instance folder in it, `i-` and a hash of the state folder and the scope. With no login session on Linux with systemd, a launch that may own runs alone with `NoSession`, and `hand_off` and `probe` report `NoOwner`, or `StateInUse` while another process holds the state folder's guard so that `start` couldn't own. On Unix the owner re-creates its lock if the folder is deleted, and touches its files so that cleaners leave them alone. On Windows it holds them open, so nothing can delete them.
- **Privileges.** A request never runs with more rights than its launch had, and never goes to another user. It runs with fewer only when the app sets `hand_down`, and the owner's handler is told what was given up (`Request::handed_down`). Otherwise `start` and `hand_off` at another Windows integrity level than the owner's get `MoreRights` or `OwnerHasMoreRights` at once. On Unix, root is another user, with an owner of its own. A launch whose rights were raised from a login (`sudo`, `run0`, `pkexec`, `doas`, and on Linux `su`; on Windows, Run as administrator with UAC on) hands off, but doesn't own by default: with no owner running, it runs alone with `MayNotOwn { why: Raised }`. Under `ElevatedOwner::NotAboveNormal` no root launch owns, nor any Windows launch above medium integrity except at the UIAccess level (0x2010). A process whose real and effective user or group ids differ, as a setuid or setgid program's do while it runs with its rights, takes no part: it gets `Excluded`. On Windows, so does a sandboxed one: below medium integrity, in an AppContainer, or with a restricted token. On Linux the process's ids and its folders' owners are read with system calls, so `fakeroot` doesn't change them.
- **Windows.** The owner listens on a named pipe. Every integrity level from medium up shares one lock per state. The owner marks its level with a second locked byte in it, and publishes its pipe's random name in its level's address folder (`run` at medium, `run-high` when run as administrator), labelled at that level. The pipe has a user-only access list and an integrity label. The owner checks each launch's token; the launch checks the address folder and the pipe against the level the owner's lock shows, and that the pipe is its user's. The crate's folders have access lists for the user and SYSTEM alone. The instance folder is labelled medium, so a launch at medium can use one made at high, and each address folder is labelled at its level.
- **Platforms.** `flock` and `LockFileEx` are called directly, not through std. Linux, Android, macOS, FreeBSD, NetBSD, illumos and Windows are supported; OpenBSD and DragonFly share the BSD code but aren't checked in CI. Every other target compiles, and launches there run alone with `Reason::Unsupported`.
- **MSRV** 1.85.
