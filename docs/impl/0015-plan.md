# 0015: implementation plan

The slices that build [0015](../design/0015-state-keyed-identity.md) and the open follow-ups of the other accepted records. A planning run made it on 2026-10-19. Four agents mapped the requirements and the code, three planned the slicing independently (always green, riskiest first, easiest to review), a judge merged their plans, and a critic checked the result and revised it. The answers to its open questions are in [0015-calls.md](0015-calls.md), and the requirements (R01 to R61) are in [0015-requirements.md](0015-requirements.md).

## How a slice lands

- Each slice is one commit, pushed when it is done. CI must be green on Linux, macOS and Windows (high, medium and `just levels`) before the next slice that depends on it starts. If CI fails, a follow-up commit fixes it; pushed history isn't rewritten.
- Sizes: 1 is under about 50 changed lines, 2 about 50 to 150, 3 about 150 to 400, 4 about 400 to 800, 5 more.
- The crate docs stay true at every commit. Design records in `docs/design` change only when a design is finished, or if a slice changes a design decision. This file tracks progress. The planning run spread record edits across the slices; those edits wait for the slices that finish 0015 (44 to 46).
- Every new `sys` function lands with its caller, a stub in `unsupported.rs`, and its counterpart on the other platform. Internal variants or fields that only one platform builds carry `#[cfg_attr(not(windows), allow(dead_code))]` or the Unix equivalent, as `naming::level_folder` does. Otherwise clippy fails on the other platform.
- Wire bytes change only in the commit that changes a message, with its frozen test: HELLO in 5, 9, 13 and 16; REQUEST in 18; REPLY in 5 and 17. On-disk names freeze with the slice that defines them: root bases in 7, `i-<hash>` in 12, the level marker in 20, the guard's name and modes in 25 and 26, and the Windows guard offset in 27.
- Only Windows CI can show that slices 3, 19 to 23, 31, 33, 35 and 37 work, or the Windows halves of 5, 8, 10, 12, 16 to 18, 27 and 30. Locally, `just windows` shows only that they compile and pass clippy. macOS CI checks the realpath half of 7. The Linux job, with fakeroot and bubblewrap installed, checks 6 and 38.

## Order and parallel work

The dependencies allow up to six slices at once. Most slices still run in order, because they share files: about 30 touch `lib.rs`, 17 touch `launch.rs`, about 20 touch `windows.rs` and about 15 touch `unix.rs`. Parallel branches would conflict at every rebase, and each fix would need another Windows CI run.

The exception is the first wave. Slices 1, 2, 3, 6 and 14 touch nearly separate files: the wire tests, the process tests, the Windows probe, the Unix syscalls and a new `level.rs`. They are built side by side in separate worktrees, then land one commit at a time in order. Slice 4 follows once slice 3's Windows run has printed its facts. Slice 8 follows the wave, so its rename of `AppId::new` also covers their new code.

The longest chain of dependent slices weighs 34 of the plan's 114: 8, 10, 11, 12, 25, 26, 27, 30, 32, 33, 44, 45, 46.

### 5. Answer refused launches with a cause, and read unknown causes as Declined

Size 3. After: 1. Covers: R21, R22, R19, R44, R53, R50, R51, R23, R61.

0015's 'refusals that answer at once on the wire'. Where an owner closes silently today, it answers REPLY REFUSED with the cause PEER. Its HELLO advertises FEATURES bit 0. A launch reads a REPLY where it expected HELLO or READY, and reads unknown refusal codes as Declined.

**Changes**

- launch.rs refused() (471-488) takes Option<&Hello>. PEER maps to Reason::Peer; WIRE, MALFORMED, UNSUPPORTED and a missing code stay WireVersion; any other code becomes Declined (today `_ => WireVersion`)
- launch.rs exchange (355-364): a REPLY as the first frame goes through refused(), so a probe can't read a refused peer as Ok
- wire.rs: refusal::PEER = 10, with comments reserving 8 PRIVILEGE, 9 SCREEN, 11 STATE and 12 PERSON. HELLO record 11 FEATURES (u32 LE; bit 0 means refusals carry a cause), which Hello::encode reads, so it isn't dead code
- server.rs: Ctx::hello writes FEATURES. Session::refused(core, code, now) is a session whose only frame is REPLY REFUSED, then Drain. Session::refuse(code, now) refuses a session that is past HELLO, and does nothing once in Drain
- unix.rs accept (1333-1345): a peer of another uid, or a failed peer check, gets a Connection with Session::refused(PEER) (shape per open question), flushed and drained, instead of `continue`. The silent close on MAX_CONNECTIONS overflow stays, because it is a retry signal
- windows.rs serve (1531-1537): a failed check_client calls c.session.refuse(PEER), marks the connection refused (so a later read neither runs check_client again nor appends a second REPLY), and falls through to pump() (1558). HELLO went out at connect, so the REPLY arrives where READY would, and launch.rs:412 already routes it

**Tests**

- launch.rs: a new #[cfg(test)] module mapping each known code to its Reason, unknown codes 8..=255 to Declined, and REPLY-first
- server.rs: a refused session writes one REPLY REFUSED PEER and no HELLO, then drains; refuse() after Drain adds nothing
- tests/handoff.rs (cfg(unix)): a fake owner flocks instance.lock in runtime_dir() and answers REPLY REFUSED PEER on instance.sock; probe and hand_off return Peer well inside the timeout
- tests/process.rs: a payload-version refusal by an owner process arrives well inside the timeout
- wire: hello_bytes_are_frozen gains FEATURES; reply_bytes_are_frozen gains REFUSED PEER

**Docs**

- Reason::Declined: 'or refused it for a reason this build doesn't know'
- Reason::Peer: the owner now says so at once
- lib.rs contract (261-270): owners never close a refused connection silently; the FEATURES record
- 0011 control 7, 0009, 0015 status line and index row

**Verified by** just ci on Linux; macOS reruns it. On Windows CI the check_client change shows only that nothing regressed, because no test reaches it until slice 17's raw client.

**Risks** A Unix launch already checks the peer's uid itself (unix.rs:529-538), so on Unix the owner's PEER refusal is defence in depth. A flood from another user fills MAX_CONNECTIONS, bounded by the drain deadline.
